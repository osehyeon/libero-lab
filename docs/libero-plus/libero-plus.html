LIBERO-Plus 교란 지도

원본 4개 스위트를 7개 축으로 흔들어 10,030개 과제를 만든 벤치마크. 이 저장소에서 어떻게 돌리는지, 무엇이 걸렸는지.

CVPR 2026 · arXiv 2510.13626 · sylvestf/LIBERO-plus · 서브모듈 4976dc3

01

같은 과제, 일곱 가지 교란

아래는 전부 같은 과제다 — “접시와 라미킨 사이의 검은 그릇을 집어 접시에 올려라”. 첫 칸이 원본이고 나머지 일곱은 각 축이 최대에 가깝게 걸린 변형이다. 이 저장소에서 plus_demo.py --render로 직접 뽑은 장면이다.

과제 이름 끝에 붙는 토큰이 곧 교란의 명세다. view_13_15_100_0_0은 카메라 파라미터고, light_31은 조명 프리셋 번호, add_11은 추가된 방해 물체다. 평가 결과를 축별로 쪼갤 때 이 이름만으로 분류할 수 있다.

Language Instructions 칸이 원본과 똑같아 보이는 것은 정상이다. 바뀐 것은 지시문뿐이고 장면은 건드리지 않는다. 그런데 논문이 발견한 가장 뼈아픈 결과가 바로 이 축에서 나온다.

02

규모

축별 과제 수. 이 저장소의 LIBERO-plus/libero/libero/benchmark/task_classification.json을 직접 세어 확인한 값이다.

교란 축과제
Sensor Noise1,601
Camera Viewpoints1,599
Robot Initial States1,550
Language Instructions1,537
Objects Layout1,525
Light Conditions1,142
Background Textures1,076

스위트별로는 spatial 2,402 / object 2,518 / goal 2,591 / libero_10 2,519 이고 합계가 정확히 10,030이다. 난이도는 1~5로 매겨져 있는데, libero_goal의 121개는 값이 null이다. 난이도로 거를 때 걸러야 한다.

03

논문이 찾은 것

95% → 30% 카메라 시점·초기 자세만 흔들어도

원본 LIBERO에서 90%를 넘기던 공개 체크포인트들이 적당한 교란에서 30% 아래로 떨어진다. 가장 취약한 축이 카메라 시점과 로봇 초기 자세다. 리더보드 최고점은 OpenVLA-OFT+ 79.6%.

언어를 보지 않는다

반대로 언어 변형에는 거의 반응하지 않는다. 추가 실험 결과 모델이 지시문을 사실상 무시하는 것으로 나타났다. 언어 조건부 정책이라면서 언어가 출력에 영향을 주지 않는다는 뜻이다.

같은 현상을 LIBERO-PRO는 반대편에서 확인했다 — 지시문을 망가뜨리거나 의미 없는 토큰을 넣어도 출력이 그대로였다.

우리가 이미 관측한 것과도 맞물린다. π₀ 체크포인트가 4개 스위트 평균 96.85%인데 libero_90에서는 18%였다 (openpi #734). 스위트를 바꾸는 것만으로도 같은 종류의 붕괴가 보였던 셈인데, 그때는 어느 축 때문인지 알 수 없었다. 이 벤치마크는 그걸 분리해 준다.

04

돌리는 법

설치는 한 번이다. 6.4 GB를 받아 9.4 GB로 풀린다.

# 저장소 루트에서
./setup-plus.sh

이후에는 아무 python으로나 실행하면 된다. 스크립트가 libero_env.require("plus")로 알맞은 venv와 설정을 잡아 자기 자신을 다시 실행한다.

python plus_demo.py --list                 # libero_spatial
python plus_demo.py --list --suite all     # 10,030

python plus_demo.py --render --category all
python plus_demo.py --render --category "Camera Viewpoints" --level 5
python plus_demo.py --render --suite libero_10 --category "Objects Layout"

--level은 1~5이고 0이 기본값으로 “아무거나”를 뜻한다. 결과 이미지는 runs/plus.png에 쌓인다.

05

설치하며 걸린 것

업스트림 README만 따라가면 막히는 지점이 넷 있었다. 전부 setup-plus.sh가 처리하지만, 직접 손댈 일이 생기면 알아둘 값이 있다.

패키지 이름이 원본과 같다

LIBERO-plus도 libero를 제공한다. 내용은 다르다 — bddl_base_domain.py, env_wrapper.py, 각 problems/*.py가 전부 바뀌었고 custom_objects.py가 추가됐다. 한 venv에 넣으면 먼저 잡히는 쪽만 살아남는다. 그래서 .venv-plus와 ~/.libero-plus로 갈랐다.

에셋 zip에 업로더의 절대 경로가 박혀 있다

HuggingFace의 assets.zip은 최상위가 inspire/hdd/project/…/LIBERO-plus-0/assets/로 시작한다. README대로 extractall하면 엉뚱한 곳에 풀린다. /assets/ 위를 잘라내야 한다.

ImageMagick이 선택이 아니다

env_wrapper.py가 모듈 최상단에서 wand를 import한다. 없으면 import libero 자체가 실패한다. 센서 노이즈를 쓰지 않아도 필요하다. macOS는 brew install imagemagick 후 MAGICK_HOME까지 있어야 하고, Linux는 apt install libmagickwand-dev에 root가 필요하다.

torch.load 버그를 그대로 물려받았다

원본과 같은 곳이 두 군데다. patches/libero-plus-fixes.patch에 담았다.

조용히 어긋나는 조합

LIBERO_CONFIG_PATH를 빼먹고 원본 venv로 plus_demo.py --list를 돌리면 에러 없이 2,402개를 출력한다. 목록은 설정 파일만 읽어서 통과하고, 렌더링에 가서야 원본 코드로 교란된 장면을 만들려다 어긋난다.

그래서 모든 스크립트가 libero_env.require()로 시작한다. 이 호출은 서드파티 import보다 위에 있어야 한다 — os.execve가 먼저 로드된 것을 버리기 때문이다.

7축 × 5단계를 한 과제에 펼친 갤러리, 이름 문법, 단계별 측정값, 알려진 결함은 libero-plus-tasks.html.

계보 전체와 다른 후속 벤치마크(LIBERO-PRO, LIBERO-X, LIBERO-Para) 비교는 libero-successors.md. 원본 벤치마크 문서는 ../libero/, MuJoCo와 회전 기초는 ../sim/.

이미지는 전부 이 저장소에서 렌더링했다. 수치는 논문이 아니라 task_classification.json에서 직접 센 값이다.
