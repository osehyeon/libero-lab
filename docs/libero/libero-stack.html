LIBERO 생성 스택

태스크 정의부터 hdf5 파일까지, 어떤 라이브러리가 어느 단계에서 무엇을 맡는지 정리했다. LIBERO 자체는 얇은 층이고, 대부분의 일은 아래 계층이 한다.

01

LIBERO

LIBERO

LIBERO

02

수집과 렌더링이 분리되어 있다

이 스택에서 가장 중요한 설계 결정이다. 사람이 시연할 때는 이미지를 저장하지 않는다.

# 4단계 — 수집이 남기는 것
model_file   # 씬의 MuJoCo XML 전문
states       # 매 스텝의 물리 상태
actions      # 사람이 넣은 7차원 행동
             # 이미지 없음

# 5단계 — 후처리가 이미지를 만든다
env.sim.set_state_from_flattened(states[i])
env.sim.forward()
obs["agentview_image"]        # 이 시점에 비로소 렌더

결과가 세 가지다.

함의근거
시연이 가볍다 — 조종 중에 렌더링 부담이 없다수집 단계는 물리만 돌린다
해상도·카메라를 나중에 바꿀 수 있다OpenVLA가 원본 128²를 256²로 다시 뽑은 것이 이 구조 덕이다
데이터셋이 커진 원인이기도 하다상태·행동은 스텝당 수백 바이트지만, 사후 렌더한 이미지 2장이 98 KB

이 재생이 성립하는 이유는 states가 MuJoCo 상태 그 자체이기 때문이다. 주입하면 접촉과 물체 위치까지 그대로 복원되므로, 몇 번을 다시 렌더해도 같은 장면이 나온다.

03

누가 누구의 종속성인가

계층이 위아래로 놓인다고 해서 패키지가 서로를 선언하고 있다는 뜻은 아니다. 설치된 배포 메타데이터에서 Requires-Dist를 그대로 뽑으면 이렇다.

패키지선언된 의존성
libero 0.1.0없음 — setup.py의 install_requires=[]
robosuite 1.4.1mujoco · numpy · numba · opencv-python · pillow · pynput · scipy · termcolor
mujoco 2.3.7absl-py · glfw · numpy · pyopengl
bddl 1.0.1networkx · numpy · jupytext · pytest
robomimic 0.3.0torch · h5py · imageio · egl_probe · tensorboard · matplotlib · tqdm

이를 의존 관계로 펼치면 이렇게 된다. 실제로 두 갈래로 완전히 갈린다.

numpy — 위 거의 모든 노드가 공통으로 의존

두 갈래가 만나지 않는다. 왼쪽은 robosuite/MuJoCo, 오른쪽은 PyTorch로, numpy 말고는 공유하는 것이 없다. 그래서 시뮬레이터만 쓸 거라면 오른쪽 가지는 통째로 설치하지 않아도 된다 — 이 세션에서 robomimic을 --no-deps로 넣고도 모든 실험이 돌아간 이유다.

그래서 설치가 번거롭다 pip install -e LIBERO가 아무것도 끌어오지 않는다. robosuite·bddl·mujoco를 전부 손으로 깔아야 하고, 버전 범위도 선언되어 있지 않아 충돌을 아무도 막아주지 않는다 — robosuite 1.4는 MuJoCo 2.3 API 기준인데 최신 mujoco를 설치하면 그대로 깨진다.

robomimic → egl_probe도 함정이다. egl_probe는 Linux 전용인데 무조건 요구하도록 선언되어 있어, macOS에서는 --no-deps로 우회해야 한다.

정리하면 제대로 선언된 사슬은 robosuite → mujoco 하나뿐이고, 위쪽 연결은 전부 임포트로만 존재한다. 계층 지도의 화살표를 패키지 관리자가 알지 못한다는 뜻이다.

04

누가 실제로 일하는가

LIBERO 소스의 임포트를 세어보면 무게중심이 분명하다.

라이브러리LIBERO가 쓰는 방식
robosuite · 59회사실상 본체. 로봇·컨트롤러·카메라·API 전부
MuJoCo · 1회robosuite에 가려져 거의 보이지 않는다
bddl · 1개 모듈bddl.parsing만. 파서 이상은 쓰지 않는다
h5py · OpenCV · Pillow저장과 이미지 처리. 물리와 무관
LIBERO의 기여는 코드가 아니다 스택의 어느 층도 LIBERO가 새로 만든 것이 아니다. 이 프로젝트가 더한 것은 130개 태스크 정의 · 6,500개 인간 시연 · 통제된 실험 설계다. 코드는 기존 라이브러리를 엮은 얇은 층이고, 그래서 libero/libero와 libero/lifelong이 서로 다른 스택 위에 앉아 있다 — 앞의 것은 robosuite, 뒤의 것은 PyTorch다.
